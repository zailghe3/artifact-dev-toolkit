# ADT Codex Runner

This repository-owned, server-to-server HTTP bridge runs Codex on the home cluster; OpenAI still hosts model inference. Codex App Server is a private stdio child used only for account lifecycle. Future job execution will use the official Codex SDK through `CodexJobRunner`; it is deliberately unavailable today.

## Deployment

Deploy `poulti/adt-codex-runner:latest` with the Compose example. Create the external `codex_runner_shared_secret` in Docker/Portainer, never in YAML. `CODEX_RUNNER_SHARED_SECRET_FILE` is preferred; supplying it together with the development-only direct environment variable fails closed. Only a single trailing newline is removed.

The Dockerfile prepares `CODEX_HOME=/data/codex`; production mounts durable storage there so images and containers remain disposable while the volume retains ChatGPT authentication. Fresh image smoke tests use the same pre-created path without a persistent volume, making it empty and isolated. Codex 0.147 requires an explicitly configured `CODEX_HOME` to already exist, so CI must not override it with a nonexistent path. PR and publish workflows intentionally use the same repository-owned image smoke script. Never copy the production volume into an image or repository. Pull and recreate manually or with Shepherd; GitHub Actions only publishes images and never operates the cluster.

Place an independently managed Cloudflare Tunnel named `adt-codex-runner` in front of the service: hostname `cr.pouchet.net`, origin `http://<home-runner-service>:8789`, Access application policy `Service Auth`, and the ADT service token as the sole identity. Access and `X-Codex-Runner-Secret` are both required for `/v1/**`. Do not expose App Server, add browser CORS, or commit Tunnel credentials.

The production Compose topology joins `cloudflared` and `codex-runner` to the private `codex_ingress` network and publishes no host port. If `cloudflared` instead runs directly on the host, add only a loopback binding: `ports: ["127.0.0.1:8789:8789"]`. Never publish the Runner on every host/LAN interface.

Device-code authentication also requires the `codex` subprocess to resolve and establish outbound TCP/TLS connections to `auth.openai.com:443`. Cloudflare Tunnel connectivity into the Runner does not prove this outbound path works. In particular, a Docker network marked `internal` blocks ordinary Internet egress unless another explicit egress path exists. Proxy-controlled environments may require the appropriate HTTP/HTTPS proxy variables. Networks that intercept TLS may require a trusted PEM bundle selected with `CODEX_CA_CERTIFICATE`, or the `SSL_CERT_FILE` fallback; neither is required by the normal deployment and no organisation-specific CA is embedded in the image. Proxy values, credentials, CA paths, and CA contents must never be logged.

The shared-secret-protected `GET /v1/diagnostics/auth-environment` endpoint performs only bounded, non-mutating checks against the fixed authentication host. It reports ordered system resolution (never addresses), the container IPv6-disable bit, separate IPv4/IPv6 TCP and verified-TLS results with allowlisted failure classes, the strictly parsed active Codex version, and `HEAD` results for `/` and `/api/accounts/deviceauth/usercode`. The device route is checked with HTTP/1.1, HTTP/2, no User-Agent (retained as a stable comparison probe), and a truthful `ADT-Codex-Runner-Diagnostic/<runner version>` User-Agent. Results contain only bounded status, challenge, redirect, content-kind, exact Cloudflare-edge, and optional three-letter colo metadata; bodies, locations, arbitrary headers, command output, stderr, addresses, paths, and credentials never leave the Runner. Diagnostics never start or poll device authentication and do not solve or bypass Cloudflare challenges.

An explicit diagnostics request runs an ADT-owned `reqwest` 0.12.28 POST matrix and one forced-IPv4 Node POST control against the exact device-auth path. Every active request sends only the retained single-byte malformed JSON body `{` and never reads a response body. The former empty-client control was retired after production returned HTTP 200: that outcome does not prove it created a device ceremony, but it makes the body insufficiently inert for repeated diagnostics. Parsers and the UI retain legacy compatibility for results from an independently deployed older Runner, while the current Runner never generates that request.

The Rust baseline explicitly selects native TLS with `use_native_tls()`, while `rustlsTls` uses reqwest 0.12.28 rustls with native/system trust roots (`rustls-tls-native-roots`). An HTTP response stops the matrix. A transport failure with a typed TLS source enables exactly one otherwise-identical `rustlsTls` attempt using `use_rustls_tls()` and then stops. A transport failure without a TLS source retains the sequential User-Agent, HTTP/1-only, no-proxy, and forced-IPv4 variants. There are no retries: the TLS path makes at most two Rust requests, and diagnostics make one four-second-bounded Node control.

The complete connection chain is: Browser -> ADT -> Cloudflare Worker -> Cloudflare Access -> Cloudflare Tunnel -> Node Runner -> `codex app-server` -> Codex Rust/reqwest client -> DNS/address selection -> TCP -> TLS -> the Cloudflare `auth.openai.com` edge -> device-auth API. A working inbound tunnel therefore does not prove outbound Codex connectivity, and a working Node probe does not guarantee identical Rust/reqwest behavior. Likewise, `ipv6Available=true` means DNS advertised an AAAA record, not that IPv6 is usable.

The previous validated pin was `rust-v0.118.0` (commit `b630ce9a4e754d35a1f33e4366ba638d18626142`). The exact official `rust-v0.147.0` release source was reviewed for this upgrade: App Server retains the initialization and account methods used here, while device authorization now obtains its client through Codex's shared auth-route HTTP-client layer rather than constructing the old login-specific raw `reqwest::Client`. The 0.147 workspace feature graph does not enable reqwest's optional Hickory DNS resolver, so the ordinary system resolver remains in its transport dependency graph. The image-local `/etc/gai.conf` preference is deliberately retained for the first controlled production comparison. `runnerAddressPolicyEffective` proves only the ordering observed by the system resolver; it never proves which address a particular Codex request selected or that the policy fixes Codex authentication.

The operator-level `disable_ipv6` sysctl is neither required nor recommended by this image and did not fix the observed production case. A `cf-mitigated: challenge` response is an upstream Cloudflare mitigation response, not an ADT authorization failure.

## Codex binary provenance and libc policy

The Runner keeps the OpenAI release at exactly **0.147.0**, sourced from the official `openai/codex` repository at the dereferenced `rust-v0.147.0` commit `be6e8eac029b183056b7e4402879f15d2c85f61b`. OpenAI's 0.147 Linux npm/release packaging selects the `x86_64-unknown-linux-musl` target. ADT does not install that package in the final image; it builds the same unmodified source for the separately supported GNU target.

ADT then uses the unchanged upstream package builder with the explicitly supported `x86_64-unknown-linux-gnu` target and upstream `dev-small` profile. This is an ADT experimental GNU/glibc build of unmodified official OpenAI 0.147 source, selected to make the controlled libc/address-selection experiment practical on hosted CI; it is neither release-equivalent nor an OpenAI-published GNU prebuilt artifact. The builder disables incremental compilation and bounds Cargo to two jobs to reduce ephemeral CI disk and memory pressure. It pins Rust 1.93.1, verifies the Git commit, writes the canonical package to a deterministic directory, validates its layout/version/target/variant/entrypoint metadata, and proves the output's GNU loader and glibc dependency before copying only that package into the runtime image. The upstream package builder's checksum-validated V8 artifact handling remains unchanged. Version and generated App Server schema gates continue to run against the final executable. Production is intentionally Linux amd64-only for this experiment. Coding jobs remain disabled. The ADT client accepts #177 protocol-v1 diagnostics that omit the new additive fields during an independent Runner rollout.

The existing IPv4 preference is the glibc `/etc/gai.conf` policy. Earlier Node/glibc resolver ordering could not establish that the npm musl Codex process followed the same ordering. The GNU build allows this image-local policy to govern Codex's system resolver path. A root-owned, read-only image marker records the already validated libc classification. Diagnostics consequently report Node's observed resolver order separately from that bounded marker and whether the policy applies; they still do not claim a particular request connected over IPv4.

## Updating the pinned Codex protocol

The Dockerfile intentionally pins the stable, non-prerelease OpenAI Codex 0.147.0 source exactly; `0.118.0` was the previous validated pin. The upgrade isolates whether the production transport failure belongs to the older HTTP implementation and does **not** claim authentication is fixed. The inspected 0.147 generated v2 schemas retain `initialize` with the existing `clientInfo` fields, `account/read`, `account/login/start` with `{type:"chatgptDeviceCode"}`, `account/logout`, and the `loginId`, `verificationUrl`, and `userCode` response. Codex 0.147 models logout with optional unit params, so its canonical client framing omits the `params` property. Codex 0.147 emits both standalone documents (including `LoginAccountParams` and `LoginAccountResponse`) and definitions such as `InitializeParams`, `ClientInfo`, and `GetAccountParams` embedded in `ClientRequest` and reached through local JSON Schema `$ref` pointers. The image validator follows each exact method branch and those structural references instead of assuming every App Server type has a top-level document. Its relevant ADT request/response surface is therefore materially unchanged. The image generates the installed binary's schemas and fails closed unless each structural method, request, and response contract is present; CI also checks the runtime version and starts App Server with the image's empty `/data/codex` without beginning a login.

Codex 0.147 still defaults `cli_auth_credentials_store` to file storage under persistent `CODEX_HOME`; no desktop keyring, new configuration, secret, proxy variable, or CA variable is required. Route-aware proxy features remain at their normal defaults and are not enabled. Operators must run auth diagnostics before the first manual production Connect attempt, and must retain the #173 diagnostics during that comparison.

`CODEX_RUNNER_CODEX_RESPECT_SYSTEM_PROXY=1` enables the sole reviewed actual-Codex experiment. It changes the process argv from `codex app-server` to `codex --enable respect_system_proxy app-server`; it defaults off, does not edit persistent configuration, and diagnostics report only its boolean state. A successful controlled A/B supports the corresponding request-identity, HTTP/2, proxy, or address-family hypothesis; all Rust failures with a successful Node POST support a Rust transport difference. These are hypotheses, not root-cause declarations. If baseline Rust succeeds while actual Connect fails, investigate the exact Codex route configuration and request next.

To upgrade the pin: update the exact version; generate and inspect the old and new initialization/account contracts; update this client and protocol fixtures if required; run Runner tests and the schema validator; run the real App Server `/v1/auth/status` image smoke test with an empty `CODEX_HOME`; then build the Docker image. The stdio device-request test, schema validation, and real CLI smoke make drift visible without committing a large generated schema. Device login remains an explicit user ceremony; normal tests and image validation never authenticate with OpenAI.

Runner protocol 1 reports capabilities so independently deployed ADT and Runner releases can coexist. There is no GitHub credential, repository clone/mutation, or coding execution authority in this release.

## Safe device-start diagnostics

Failed device starts keep the stable `device_auth_start_failed` operation code and may include only an allowlisted reason: login disabled, device login not enabled, upstream forbidden, rate limited, unavailable, rejected, transport failure, CA configuration, HTTP-client configuration, internal, or unknown. A strictly parsed HTTP status and finite integer JSON-RPC code may accompany that reason. Raw App Server errors, error data, stderr, response bodies, credentials, codes, and private paths are always discarded.

### Interpreting the Rust auth transport matrix

These bounded results are diagnostic implications, not automatic historical root-cause claims. Native-TLS failure with a TLS source followed by a rustls/native-roots HTTP response strongly implicates a difference in the TLS implementation or native-certificate-handling path; an HTTP 403 mitigation challenge still proves rustls completed TLS and moves the remaining question to HTTP/WAF handling. If both backends fail during TLS, stop varying headers, proxies, and address families and investigate bounded ClientHello/edge behavior, verification, alerts, and protocol negotiation. If native TLS unexpectedly reaches HTTP, the production outcome changed and one later run cannot establish the historical cause. This diagnostic does not alter the actual Codex auth client; forcing rustls there requires a separate reviewed follow-up.
